# Memory across chats, on the device (14 November 2026)

**Status: built and tested offline, switched off by default, nothing verified live.** Checklist row U8. Privacy wording draft for the owner: `docs/memory-privacy-wording-draft-20261114.md`.

**Update, 14 November:** the live probe (live check 1) was later run on Privatemode and passed: a relevant memory is used, unrelated ones do not leak, the answer language follows the question, a masked stand-in is kept (`docs/READINESS.md`, 14 November afternoon). Live checks 2 to 6 in the app are still open.

## What it does

The user can ask CometRow to remember a fact ("Remember that I am vegetarian", "Merk dir, dass ich in Leipzig wohne"). The app shows the exact words and asks before it saves. The memory is stored in the encrypted vault in the browser. With each later question the browser picks the few memories that fit and puts them in front of the question. The server stores no memory and no profile. It has no code for this feature.

## The switch

`VITE_MEMORY=1` at build time, in `src/device-features.ts`, like `VITE_READ_ALOUD`. Off by default.

Why a build switch and not `inference.memory` in the deployment config: the feature needs nothing from the server. No route, no status field, no count, no stored value. A server switch would be the only memory-related thing the server knows, and the claim "the server has no part in memory" is simpler to keep true without it. The cost: switching it on or off needs a new build of the web app, not a config edit. If the owner wants to switch it per deployment without a build, a status field can be added later in a few lines.

With the switch off: no Memory section in Settings, no "Remember this" button, no question to save, no row in the context review, no note under answers, and no memory is read or sent. Memories that are already in a vault stay there untouched, still go into backups and are still restored, so nothing is lost when the switch is turned off and on again.

## Decisions

**1. How a memory is created: only when the user asks.** Three ways, all explicit:

- The user sends a message that starts with "Remember that ...", "Remember: ...", "Merk dir ...", "Merke dir ..." or "Merken Sie sich ..." (with or without "please" / "bitte"). The app does not send it. It shows "Save as a memory?" with the words after the request, which the user can change. Buttons: Save memory, Send as a message instead, Cancel. Saving costs no allowance and makes no request.
- The "Remember this" button under the user's own message opens the same question with that message.
- The Memory screen in Settings has a field to add one.

Not built: automatic extraction by the model (costs requests and tokens, and stores things the user did not expect) and on-device suggestions ("Save this as a memory?" when the user states a fact). The suggestion idea was left out because simple rules that find "a stable fact about the user" either fire too often or miss most cases, and a suggestion on a health sentence would break rule 4. No extra model request is made for memory anywhere.

A sentence that ends with a question mark ("Remember that film?") is not treated as a request. A false alarm costs one tap on "Send as a message instead".

**2. What is sent.** A short block in front of the latest question, in the same message:

```
[Notes the user saved about themselves on their device. Use a note only where it helps with the message below. Do not mention the notes unless asked. They are not part of the message and do not set the reply language.]
- I am vegetarian and allergic to peanuts.
- Ich wohne in Leipzig.
[End of notes]

What can I cook tonight?
```

- At most 8 memories and at most 1,200 characters of memory text per question. The fixed wrapper adds about 250 characters.
- The memories are chosen on the device by the same word-overlap ranking as passages of large documents (`src/passage-retrieval.ts`: German and English, umlauts folded, compounds matched at half strength). The question before the current one counts half, so a short follow-up keeps its topic. A memory far weaker than the best match is left out.
- Up to 3 memories can be marked "Always include". They go with every question in chats that use memory, and they count toward the 8 and the 1,200.
- If no memory matches and none is pinned, nothing is added. The request is then byte for byte what it is today.
- Under each answer a line says "2 memories were sent with this question". Opening it lists them. Only the ids are stored with the answer, so the list shows the memories as they are now, and a deleted memory shows as "Not available". "Forget all" therefore leaves no memory text behind in saved chats (apart from what the user typed and the model answered in the chat itself).
- The chat menu has "Use memory in this chat". Unticked, no memory goes with questions in that chat, pinned ones included. The choice is saved with the chat.
- The context review ("Included context") has a row "Memory notes" with the size of the block for the current draft. The block counts toward the input limit. If it does not fit, the app says the context is too large and sends nothing, as for any other part.

Why in front of the question and not in the instructions: the instructions and all earlier turns stay exactly as they were, so the provider's prompt cache for them is not broken when the chosen memories change, and the other request paths (code tool, pictures) keep their message positions.

**3. Limits.** 200 memories, 300 characters each, so at most 60,000 characters in the vault. A memory is one line: line breaks become spaces. The same words (ignoring case and spacing) cannot be saved twice. Each memory can be edited and deleted. The list shows "Always include" first, then the newest first. A search field appears above 5 memories.

Backup and restore: the encrypted vault backup includes the memories. Restore adds them to the ones already there, skips ones with the same words, and stops at 200 (the rest of that backup's memories are left out; conversations are not affected). A backup of a vault without memories is unchanged, so an older build can still read it. The account data export (`src/AccountExport.tsx`) is unchanged: it never held vault content, and the server has no memory to export.

**4. Sensitive data.** The app never suggests a memory on its own, so it never suggests saving a health fact. There is no health detector for text in the code base today (`src/health-consent.ts` only records a consent choice), so nothing stops a user from saving a health fact on purpose. The Memory screen and the save question say plainly that a memory is sent to the protected model with questions it fits, and the screen asks the user to think twice before saving health details. Identifier masking covers memories like any other text: an email address or IBAN in a memory leaves the device as a stand-in (`{{EMAIL-1}}`), is counted in the "kept on this device" note, and is put back in the answer. In the vault the memory is stored as typed.

**5. The instruction to the model** is the first line of the block (above). It is only present when a memory is sent.

## Vault rules

- Memory works only with an unlocked vault. A locked vault, or no vault yet: nothing is read, nothing is saved, nothing is sent. The Memory screen says "Unlock your vault to use memory", and the save question says the same and offers no Save.
- The memories are one encrypted record in the vault's `meta` store, sealed with the vault key and the label `memories-v1`, like projects. An older vault has no such record and reads as "no memories". No database upgrade is needed and existing vaults are not touched.
- Changing the vault passphrase re-encrypts the memories with the new key.
- "Forget all" deletes the record itself. No encrypted empty list stays behind.
- "Delete everything on this device" deletes the vault database, memories included. The confirmation says so while the switch is on.
- A change to the memories locks other open tabs of the same account (as deleting a chat does), so no tab keeps sending a memory that was deleted in another.
- Incognito chats: no memory is read or sent, the "remember" question does not appear, and the "Remember this" button is not shown. The Memory screen in Settings still works from there, because it is not part of the chat.
- Lock, sign-out and reload drop the decrypted list from the page.

## What the server sees

Nothing new. No server file was changed. Memory text leaves the device only inside the encrypted request to the model, as part of the question. Our relay passes that package on and cannot open it. Two honest side effects:

- A question with memories is up to about 1,500 characters longer. Where our records hold token counts per request, those counts are a little higher. They do not say why.
- The provider's secure server processes the memory text like the rest of the question, and its short-term handling (prompt cache, retention) applies to it in the same way.

## Cost

No extra requests. Per question with memories: typically 1 to 3 notes, about 50 to 150 extra input tokens. Worst case (8 notes, 1,200 characters plus wrapper): about 400 to 500 tokens. At EUR 0.20 per 1M input tokens (owner's note for the Fast model) the worst case is about EUR 0.0001 per question. Allowance units per message are unchanged.

## Limits, stated honestly

- The ranking matches words, not meaning. "What can I cook tonight?" does not find "I am vegetarian". The user can pin such a memory. A question that shares one ordinary word with a memory ("time" and "part time") can pull that memory in.
- The reply-language rule looks at the user's latest message, and the block stands in that message with an English first line. The block says it does not set the reply language. Whether the models obey is not verified.
- Whether the models use notes only when relevant and do not mention them is not verified.
- The note under an answer shows today's wording of a memory, not the wording at the time.
- Memories restored past the 200 limit are dropped without a message.
- The trigger phrases are a fixed list. "Remember I am vegetarian" (without "that") is sent as a normal message.
- An unreadable memory record (for example damaged storage) makes memory silently empty until the record is replaced; adding a memory then fails with "could not be changed".
