## 2026-10-22 (later) — follow-ups: retry/backoff, live attestation-only run, CA hygiene

### Retry with backoff and transient-vs-verdict distinction [V by unit tests]

- After a failed audit the state retries at bounded delays before the normal cadence resumes: defaults 1, 2, 4 and 8 minutes (`retryDelaysMinutes`, up to 8 entries of 1..60 minutes, each at most one interval; `[]` disables retries). A success resets the schedule; `stop()` clears it.
- `runAttestationAudit` now reads stderr (bounded 16 KiB, never stored or surfaced) solely to classify a failure that happened **before any verdict**. A result is `transient: true` only for our own timeout, or exit 1 with no JSON record on stdout and a network-shaped error on stderr (`no such host`, `connection refused/reset`, `i/o timeout`, `deadline exceeded`, `dial tcp`, `tls:`/`x509:` handshake or trust errors, `unexpected EOF`, rate limit, HTTP 429/5xx, the CLI's `fetch error:` prefix). A record with `status: fail`, any exit-0 disagreement (digest, host, expiry, key) and any other pre-record error are verdicts and are never transient.
- `shouldBlock()`: a verification failure blocks immediately regardless of retries. A transient error keeps serving only while all three hold: the previous success is within the maximum age, its witnessed `freshness_expires_at` has not passed, and a retry is still pending (scheduled or running). When the retries are exhausted, or the previous success is stale or expired, or there was never a success, it blocks. Net effect: one transient error can extend serving on the previous evidence by at most the sum of the retry delays (15 minutes at defaults) within the existing 24-hour maximum age; it can never admit a request the previous evidence would not have admitted.
- A TLS trust or handshake failure toward the attestation endpoint is classified transient. That is deliberate: it is a relay-network condition, not a statement about the enclave, the browser still verifies independently, and the extension is bounded by the retries; after them the relay blocks.
- Tests added (`tests/attestation-audit.test.ts`, now 21 tests): `netfail` fixture classified transient, `crash` (non-network pre-record error) and `fail` (record) not transient, timeout transient; state: transient with no prior success blocks, transient with current success and pending retry serves, serves through the second retry, blocks when exhausted, blocks when the prior success is past the maximum age or its witness expired, verification failure blocks immediately with retries left, real-timer backoff (30/60 ms) runs the retries and resumes after a success, retries longer than the interval rejected; config: default `[1,2,4,8]`, `[]` accepted, `[1,2,4,8,16]` with a 15-minute interval rejected, nine entries rejected, `0` rejected.

### Finding: the slim base ships no CA store [V, fixed]

`node:24-bookworm-slim` has no `/etc/ssl/certs/ca-certificates.crt`; Node uses its own bundled roots, but the Go CLI uses the system store, so in the image as first built every CLI TLS connection (enclave, GitHub witness, Sigstore TUF) would have failed with `x509: certificate signed by unknown authority` even on a clean network. Fix in both Dockerfiles: the `tinfoil-verifier` stage exports Node's bundled roots (`require('node:tls').rootCertificates`, pinned by the base image digest, no package manager, no build secret, nothing host-specific) to `/out/etc/ssl/certs/ca-certificates.crt` (`0444 root:root`, directory `0755`), asserts more than 100 certificates, and the runtime stages copy that directory to `/etc/ssl/certs/`. An earlier variant with `COPY --chmod=0444` of the file alone left the created directory unreadable by `node` and was replaced before commit. Verified in the final image: `/etc/ssl/certs/ca-certificates.crt` is `0444 root:root` (181,305 bytes, 121 certificates), readable as uid 1000; a CLI run through that store from this workstation fails only at the antivirus-intercepted certificate ("unknown authority"), which also shows the antivirus root is not in the store. Trade-off [D]: the Go CLI now trusts exactly the root set Node trusts; Render's own egress is not intercepted, so no proxy CA is needed there.

## What was built

A relay-side, **partial, block-only** attestation audit, implemented on branch `worktree-agent-a78629d04463947fc` from `codex/development-handoff` commit `7ce181a`, following section 4 of `docs/relay-mitigation-assessment-20261021.md` narrowed as follows: the relay does not publish anything to the browser and the browser compares nothing. The relay runs the supplier's pinned CLI on a timer and can only **refuse** to forward.

Plain statement of scope [D]:

- The relay can only refuse requests. It never supplies, replaces or validates the key the browser uses. The browser's maintained `tinfoil` npm verifier 1.2.2 remains the only source of the encryption key, and every request still requires the browser's own verification exactly as before.
- It guards against stale or revoked supplier evidence (a freshness witness that is no longer renewed, an endorsement the supplier has withdrawn, a release that is no longer witnessed) and against a supplier release the browser would otherwise still accept because 1.2.2 consumes no freshness witness and enforces no maximum release age.
- It does **not** guard against a malicious operator. The operator controls the relay, the binary, the configuration and the timer; a compromised relay can at most cause refusal of a correct enclave, never acceptance of a wrong one, because the browser's verification is unchanged and remains an independent necessary condition.
- The CLI's V3 checks are **beta** on every supplier page read ("CLI commands that use V3 attestation to verify enclave connections are beta while deployment is ongoing"; "Features that depend on V3, including workload release pinning and freshness checks, share that status"). Revocation sources consulted by V3 are not documented by the supplier; "revocation" here means endorsement withdrawal observed through witness expiry.
- Freshness is bounded by the audit cadence plus the seven-day witness: a withdrawn or stale release is refused at the latest at (cadence interval) + (remaining witness validity, at most seven days). With the default six-hour cadence that is up to seven days six hours; the transient-error retries can add at most the sum of the retry delays (15 minutes at defaults) on top. The supplier's own page says to "use an SDK's connection-time verification for real-time guarantees"; the audit is not that.

The optional `proxy_ca` build secret does not apply to the `ADD` fetch (BuildKit performs it outside the stage); a managed build proxy that intercepts GitHub would fail the checksum, which is the intended outcome.

## Code [V by unit tests]

- `server/attestation-audit.ts`: `runAttestationAudit({ binary, target: { origin, repository, releaseDigests }, timeoutMs })` spawns `tinfoil attestation verify -e <host> -r tinfoilsh/<repo>[@sha256:<digest>] -j` (the digest is pinned on the command line when the qualification names exactly one; otherwise containment is checked), `shell: false`, stdin ignored, stdout capped at 64 KiB, stderr read only for transient classification, environment limited to `TINFOIL_NO_UPDATE_CHECK=1`, `PATH`, `HOME`, the proxy/CA variables mirrored from `server/network.ts`, and (Windows test double only) `SystemRoot`/`TEMP`. No API key or other secret is ever passed. It parses only the exit code and the documented JSON record fields `status`, `enclave`, `digest`, `keys.enclave`, `keys.connection`, `freshness_expires_at` (field names confirmed against `attestation.go` at the tag and against the live record above) and returns `{ ok, checkedAt, releaseDigest?, keyFingerprint?, freshnessExpiresAt?, reason?, transient? }`. It never throws: invalid options, spawn failure, timeout, non-zero exit, malformed or oversized output, host mismatch, digest outside `releaseDigests`, missing or past `freshness_expires_at`, and endorsed-vs-connection key disagreement all yield `ok: false` with a fixed reason. `attestationAuditGuard(state?)` is the Express middleware factory; `createDeploymentAttestationAudit(config)` builds the state from deployment configuration.
- `server/attestation-audit-state.ts`: in-memory state refreshed by an unref'd timer; defaults interval 360 minutes, maximum age 1440 minutes, timeout 120 seconds, retries 1/2/4/8 minutes, binary `/usr/local/bin/tinfoil`. `shouldBlock()` as described under the follow-up section. Disabled state never blocks. A process-wide state is installed by the deployment entrypoint and is disabled until then, so local development and the existing test suites are unaffected.
- `server/deployment-config.ts`: optional `attestationAudit` block `{ enabled, origin, repository, releaseDigests[1..4], binary?, intervalMinutes? (15..1440), maxAgeMinutes? (15..10080, >= interval), timeoutSeconds? (5..300), retryDelaysMinutes? (0..8 entries of 1..60, each <= interval) }`, strict, defaults applied on load. The restricted deployment carries no qualification report today, so the audit target is named here with the same validation rules as `shared/contracts.ts`.
- `server/deployment-process.ts`: when the block is present, creates the state, installs it process-wide, starts the timer and first audit without delaying `listen` (the guard refuses until the first success), and stops the timer on shutdown.
- `tests/attestation-audit.test.ts` (21 tests) with `tests/fixtures/fake-tinfoil-cli.mjs` standing in for the binary: pass, pinned-digest pass, non-zero exit with and without a record, transient network error, timeout, malformed and oversized output, expired witness, unqualified digest, host mismatch, key mismatch, missing binary and invalid options, disabled state, blocking before first success / after failure / past maximum age / after witness expiry, the transient and verdict paths listed above, throwing runner, shared in-flight run, timer refresh, guard 503 body and pass-through, process-wide installation, fail-closed guard, deployment-config acceptance and rejections, and the Dockerfile pin (version `0.19.10`, 64-hex checksum, `ADD --checksum`, `sha256sum -c`, read-only `COPY --from=tinfoil-verifier` of the binary and the CA directory only, CA store from Node's roots and not from a build secret or apt, `TINFOIL_NO_UPDATE_CHECK=1`, pinned base digest, no installer script or `tinfoil update` instruction). ## Wiring for the main track (not done here; `server/app.ts` untouched)

Add exactly one line in `server/app.ts` before the relay route `app.post("/api/inference/v1/chat/completions", ...)`:

```ts
app.use("/api/inference", attestationAuditGuard());
```

with `import { attestationAuditGuard } from "./attestation-audit";`. While `shouldBlock()` is true the guard answers `503 {"error":"Protected inference is temporarily unavailable. No request was forwarded."}` with `Cache-Control: no-store`; the body never names the reason. All other routes, including `/api/status`, are untouched. Without a deployment `attestationAudit` block the guard is a pass-through.

Deployment: add to the render config file (`/etc/secrets/render-config.json`) a block such as `"attestationAudit": { "enabled": true, "origin": "https://<qualified host>/", "repository": "tinfoilsh/<qualified repo>", "releaseDigests": ["<pinned digest>"] }`. The first audit starts with the server; until it succeeds, and after any failure, the relay refuses. A failed audit never stops the process.
