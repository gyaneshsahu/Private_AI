**3.1 Usage and cost display.** Both ledgers' `summary()` and the shared `RequestAllowance` type now carry the current period's `meteredRequests`, `promptTokens`, `completionTokens`, `costUsd` (decimal string summed exactly from `usage_metrics.cost_usd` as scaled integers, omitted when no metered request carried a cost) and `unmeteredRequests` (settled requests without metrics: interrupted, cancelled or uncertain). No migration. The account page moved to `src/AccountUsagePage.tsx` with separated plan, metering and no-plan components (`src/AccountUsage.tsx` re-exports it for the existing mount points); formatting lives in `src/account-usage-format.ts`. It shows requests used and remaining, the period end, token totals, the published cost with the sentence "Cost is at published rates for completed requests only; interrupted requests are billed by the provider but cannot be counted here", and "No plan is active for this account yet" when there is no allowance. The PostgreSQL ledger's `metrics()` returned an empty string for a zero cost (`"0.000000000000".replace(/\.?0+$/, "")`); it now returns `"0"`. The browser spec `tests/browser/account-usage.spec.ts` was updated to the new wording and asserts the token and cost lines; Playwright was not run in the worktree.

**3.2 Entitlement from test-mode receipts.** `server/billing-entitlement.ts`: `grantEntitlement` (ledger-agnostic) turns an `active_observed` assessment of a test-mode receipt for a known price into a request allowance via the existing `createAllowance`, with the period ID `ent-<subscription>-<periodEnd>` so repeated or duplicate receipts grant nothing twice; `applyBillingEntitlement` is the PostgreSQL step that reads the latest assessment of a reconciled, non-live receipt, resolves the bound open account and calls the grant under a schema advisory lock and the recovery gate. The plan table is in code: `rehearsal-monthly`, 200 requests, 31-day nominal period; the allowance starts at the later of period end minus 31 days and the account's previous allowance end, so a 28-day provider month cannot overlap and a 31-day one leaves no gap. Refused: live mode, non-active or unreconciled receipts, unknown prices, plans without terms, past periods, closed or unbound accounts, and any overlap with an allowance the step did not create (operator grants are never extended). No migration: the allowance row is the durable record, so the migration count stays 13 and the usage fixture is unchanged. Both ledgers gained `hasAllowance(periodId)` and `lastAllowanceEnd(accountId, endsAt)`. An allowance is still not chat access: inference stays behind provider qualification.

**3.3 Retention activation proposal.** `docs/retention-activation-proposal-20261022.md`, no code. Key findings: the code does not delete inactive accounts, only explicitly closed ones seven days after the request; the only purge function hard-refuses any database but the synthetic one and requires the whole service quarantined; the runtime role cannot delete users or stamp `purgedAt`; no code writes `holdUntil`; nothing on the hosted database is eligible because closure needs an email proof and email is disabled there; the three-day Render PITR window, not the fourteen-day registry figure, bounds hosted backup recovery.

**3.6 Time-to-first-token.** `evaluation/request-timing.ts` measures in the browser, per request, from the last pre-send status ("Receiving a protected response…") to the first non-empty content delta and to the resolved final usage frame, plus the preparation time before the request left; `evaluation/local-client.ts` records it as `client.requestTimings` in the runner's `result.json` and `evaluation/review-result.ts` passes it through the summary, accepting older records without it. No server change; no experiment was run.
