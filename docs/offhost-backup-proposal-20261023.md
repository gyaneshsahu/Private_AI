# Off-host encrypted backup and separately held recovery key - proposal, 23 October 2026 (plan 7.2)

Status: proposal for the owner's approval. Nothing is purchased, generated or configured by this document. Facts marked **[recorded]** come from the repository; prices are those recorded on 20 October in `docs/development-deployment.md` and must be re-checked at purchase.

## What exists today

- The hosted account database is Render PostgreSQL in Frankfurt with Render's own point-in-time recovery (a three-day window on the paid tier) **[recorded]**. It lives in the same provider account and failure domain as the service: losing the Render account, a billing lapse, or a provider-side deletion loses the backups with it.
- The invite registry (SQLite) has an off-host path already: `scripts/windows-backup.ps1` pulls an encrypted snapshot to a protected folder on the owner's Windows machine, encrypted with `age` to a recipient whose identity is held in the Windows credential store under a named entry, with seven-day retention, verification receipts and an hourly monitor **[recorded]**. Its documented weakness: it runs only while that computer is on, and its alerts cannot work off-computer.
- Content is never in any backup: conversations, documents and search text do not exist server-side. A backup holds identities, sign-in methods, passkey public keys, sessions, security events, usage counts, billing identifiers and closure receipts.

## Proposal

**Scope.** A nightly logical dump of the account database (`pg_dump --format=custom`, every schema the runtime uses, no roles or passwords) plus the invite registry archive, each encrypted before it leaves the producing machine, stored on a host that is not Render and not the owner's PC, with the decryption key held only by the owner.

**Encryption and key custody (the part that matters most).**

- Encrypt with `age` to a public recipient key. The producing job needs only the public key, so no secret able to decrypt a backup ever exists on Render or on the storage host.
- The private identity is generated by the owner on their own machine, never by the agent, never on a server, never in git. Two copies: one in the owner's password manager, one on paper in a sealed envelope kept apart from the laptop. The existing registry backup identity can become the first copy if the owner prefers one key for both archives; a second key for the database is cleaner because the registry key already exists on the PC that runs the registry backup.
- Key rotation: generate a new identity, add its recipient to the job, re-encrypt the retained archives, retire the old identity after the retention window. Documented, not automated.
- Loss of the identity means the off-host backups are unreadable. That is the intended property; the point-in-time recovery on Render remains the short-window fallback.

**Runner options.**

| Runner | For | Against |
| --- | --- | --- |
| 1. Render Cron Job in Frankfurt (recommended) | Reaches the database over the private network with the existing connection string; runs when the owner's PC is off; same region | A separate paid service type on Render (price to check); needs the SFTP credential as a Render secret |
| 2. The owner's Windows machine (extend `windows-backup.ps1`) | Pattern, tooling, receipts and monitor exist; no new secrets on Render | Only runs while the PC is on; needs the external database URL opened to the PC's address; the recorded weakness remains |
| 3. GitHub Actions schedule | Free | Database credentials in a third party's secret store; rejected |

**Retention.** Seven daily archives, rolling, consistent with the trial backup policy, plus one archive kept 35 days for a longer look-back. Purged account data therefore disappears physically from backups within 35 days at most; the privacy policy's "what we cannot delete" section must state this window once approved.

**Verification.** Every run writes a receipt (name, bytes, SHA-256, start time) next to the archive and emits a heartbeat to the alert service proposed in plan 7.3; a missing heartbeat is the alert, not a failed log line. A restore rehearsal into a throwaway database with the owner's identity, timing the restore, belongs to plan 7.1 and is the only proof that the backups are usable. `scripts/backup-health.ts` already validates receipts and archives for the registry path and can be extended to the database archive.

## Decisions for the owner

1. Destination: A (Storage Box) or B (object storage with lock).
2. Runner: 1 (Render Cron Job) or 2 (owner's PC).
3. One `age` identity for both archives, or a second one for the database.
4. Retention 7 daily plus 1 at 35 days, or 7 only.
5. Budget: about EUR 3.20 net per month for A, plus the cron job price on Render if runner 1.

## What the agent will do after approval

Write the dump-and-encrypt job (shell plus a small TypeScript receipt writer reusing the `backup-health` receipt schema), its script or image target, the restore procedure for 7.1, the policy sentence on the physical deletion window, and the checklist row. The agent will not generate keys, create accounts, or set secrets; those are owner actions by the standing rule.
