"The enclave sends queries or URLs to Exa over TLS and returns the results to the caller through the verified transport." Our browser verifies only the router; whether the router verifies the websearch enclave's attestation before using it is not stated in the read pages **[unknown]**. The retained v0.0.158 compare shows the router opening an MCP session to a server named `websearch` with `router_search` and `router_fetch` tools [independently verified from the retained patch].

Supplier-stated limits that matter for our privacy promise:

- The query is composed by the model from conversation context inside the enclave; it can reflect private conversation content. The January 2026 blog says this risk is addressed "through legal frameworks and careful prompting", and in the API the PII filter is **opt-in per request** ("Omit the field to skip the check"), uses OpenAI Privacy Filter, is "primarily English and can miss sensitive text or label public information as private", and "may cover only part of a sensitive value, so neither `masked: true` nor the presence of `pii` guarantees the remaining query is free of PII." - The blog states a collusion/timing limit: "If Tinfoil and our search provider were both compelled under law, a timing correlation attack could link specific users to specific queries" and "Our current user base is small enough that a timing correlation attack is viable" (January 2026; current anonymity-set size **[unknown]**). [supplier statement]
- Prompt-injection filtering is also opt-in; the blog (January) says injections are not viewed "as a significant risk"; the current guide offers a safeguard-model filter that drops offending results and pages. [supplier statement]
- On the Responses API, `previous_response_id` carries "prior search results and fetched pages" forward across turns. Where that state is held and for how long is **[unknown]**; it sits uneasily beside "not retained after the response is returned" and should not be used.

## 3. Design sketch: what enclave search would change

### What exists today [independently verified from code]

`src/verified-chat.ts` sends one fixed body — `model`, `messages`, optional `response_format` and calculator `tools`, model-specific `chat_template_kwargs`, `stream`, `stream_options.include_usage`, `max_completion_tokens`, a fresh `user_cache_secret` — encrypted with EHBP to the verified router key and posted to `/api/inference/v1/chat/completions`. `server/app.ts` accepts only that route, checks `X-Tinfoil-Enclave-Url` against the approved origin, forwards the ciphertext to `/v1/chat/completions` with `Authorization`, `Content-Type`, `Accept` and `Ehbp-Encapsulated-Key`, and settles the allowance on transport completion; it sends no `X-Tinfoil-Request-Usage-Metrics` header and reads no trailer. Research is a separate plaintext path: the browser proposes a query, `server/research.ts` `Approvals.issue` validates it with `disclosureSchema` (search text 2–400 characters or an HTTPS page URL), names the recipient ("Brave Search API" or the page host), the user approves the displayed disclosure, `/api/research/execute` consumes the approval once and calls Brave; results return as `Source` records with `evidenceKind` `search-excerpt`, `page` or `llm-context`. `src/App.tsx` sets the sticky `temporarySearch` flag when a search approval succeeds, and `containsTemporaryResearch` in `src/saved-conversation.ts` refuses to save or reopen any state carrying `researchQuery`, a temporary `evidenceKind` or a temporary `sourceSnapshot`. The qualification record in `shared/contracts.ts` includes the `noExternalTools` check, whose recorded evidence is "Our fixed inference request includes no tool options" ([provider-qualification.md](provider-qualification.md), evidence ledger).

### Chat completions with `web_search_options` (the smaller change) [engineering assessment]

Keep the single relay route and the local SSE parser. Add one top-level field, `web_search_options`, only on turns the user has explicitly enabled, with conservative values: `search_context_size: "low"`, `filters.allowed_domains` where the task permits, `max_age_hours` where freshness matters, and `pii_check_options: {}` always. Do not send `X-Tinfoil-Events: web_search` in a first test: it embeds `<tinfoil-event>` markers inside `delta.content`, which our reply consumers would otherwise display as text. Without markers, citations arrive as `delta.annotations[].url_citation` with `url`, `title`, `start_index` and `end_index`; the reply stream consumer would collect them into `Source` records with a new `evidenceKind` (for example `enclave-search`), each carrying a title and URL but **no provider snippet**: on chat completions the enclave returns the model's grounded prose and citation spans, not the retrieved excerpts. The usage chunk still arrives through `stream_options.include_usage`. Nothing else in the body changes, so the frozen request shape remains auditable as "one fixed body plus one optional field".

Post-hoc query disclosure requires either the marker header (whose terminal `search` marker carries `action.query`, the pre-masking query, plus `sources: [{url,title}]` and the `pii` report) or the Responses API. If the founder wants the user to see what was actually searched, a second step would add the marker header and a strict marker stripper (the guide's regex `\n?<tinfoil-event>[\s\S]*?</tinfoil-event>\n?`) before any text reaches the renderer; a marker that fails to parse must be dropped, never shown.

### Responses API with the `web_search` tool (the larger change) [engineering assessment]

`/v1/responses` is a different endpoint (a new relay route and allowlist entry), a different body (`input` plus `tools: [{type: "web_search"}]`), a different event vocabulary (`response.output_item.added`, `response.web_search_call.*`, `response.output_text.delta`, `response.output_text.annotation.added`, `response.completed`) and a flat annotation shape. It gives the cleanest query transparency: each `web_search_call` item carries `action.query` or `action.url`, and `include: ["web_search_call.action.sources"]` lists the URLs each search returned. It also introduces `previous_response_id` server-side state, which we would not use. This surface replaces our SSE parser, reply consumers, calculator and contract paths rather than extending them; it is not a candidate for a first bounded test.

### The user-approved query flow changes in kind, not in degree [engineering assessment]

The current flow lets the user read and amend the exact query and see the recipient before anything leaves the browser. With enclave search the model composes queries autonomously and may issue several searches and page fetches per request; the supplier's blog explicitly rejects per-query approval ("A single prompt can trigger multiple searches, leading to approval fatigue"). The honest replacement is a **per-turn capability disclosure**, not a query disclosure: before sending, the browser shows that this reply may search the web through Tinfoil's enclave and Exa, that queries are composed by the model from the conversation, that PII masking is partial and English-biased, that the backend will not see the queries, and that the conversation becomes temporary. `Approvals.issue` would record a new disclosure kind (for example `enclave-search`) whose value is the turn identifier, not query text, so the server keeps no plaintext at all; `consume` would mint a short-lived capability the browser must present as a request header, which the relay checks before forwarding. The relay cannot verify that an encrypted body omits `web_search_options` when no capability is present, so the enforcement is browser-side policy plus after-the-fact settlement: the relay must send `X-Tinfoil-Request-Usage-Metrics: true` and read the streaming trailer, charging the account for `web_search_calls` and `cost_usd` and treating any request with `web_search_calls` present but no capability as a policy violation to report. Reading an HTTP trailer requires a lower-level client than the WHATWG `fetch` the relay uses today.

### The sticky temporary-session boundary [engineering assessment]

Set `temporarySearch` **before** the request is sent, when the turn carries `web_search_options`, not after results arrive: the assistant text itself is search-derived even when no citation is emitted. Extend `containsTemporaryResearch` and the provenance backstop to the new `evidenceKind` and to messages flagged as enclave-grounded, so legacy-state imports cannot launder them. Keep the existing rules: no application persistence, no exports, legacy records untouched, Copy answer available as the provisional explicit action, known citations navigable without referrer and arbitrary model links inactive. The inline `[label](url)` links the enclave inserts into the prose must be matched to annotation spans and rendered through the existing known-citation path only.

### Qualification gates and frozen evaluations [engineering assessment]

Enabling the tool contradicts the recorded `noExternalTools` evidence; that check must be re-described in the qualification record as "tool use limited to the supplier's in-enclave search under an explicit per-turn capability", with its own evidence, before any report could list it — this document does not do so. The frozen research cases and the citation audits depend on retrieved source text to check quotations; the chat-completions path returns none, so those audits cannot run against enclave search. Any test needs a new, separately frozen packet whose expectations are written for title-and-URL citations plus manual same-session source comparison, as the 12 October entries already require for fresh retrieval.

## 4. The per-request fee and `X-Tinfoil-Usage-Metrics`

Mechanism [supplier statement]: send `X-Tinfoil-Request-Usage-Metrics: true`; the enclave returns `X-Tinfoil-Usage-Metrics` "as a response header for non-streaming requests, as an HTTP trailer for streaming requests", a comma-separated `key=value` map. Documented example: `prompt=1000,completion=500,total=1500,model=gpt-oss-120b,web_search_calls=2,cost_usd=0.052`. Field semantics from the proxy guide: `web_search_calls` is the "Number of web searches and page fetches the model performed. Only present when at least one ran, which is also when the web search fee applies. Enabling web search without the model using it does not add this field or the fee."; `cost_usd` is the "Total cost of the request in USD, including the web search fee when `web_search_calls` is present and `other_cost_usd` when present. Omitted if any component of the cost is unknown."; "These headers report usage at published rates, before account-specific exemptions."; "Parse the value as a map rather than by position, since optional fields may be added between existing ones." The web search guide adds: "The fee is charged once per request regardless of how many calls the model made."

Amount: **not published** [independently verified]. The pricing page carries no API price table at all ("API access is pay-as-you-go with per-model pricing based on input and output token usage"; the only search mention is the Chat plan's "Ability to search the web"); the web search guide, proxy guide, model catalog page and changelog state no figure; "Spending limits and per-key caps are soft." The only number anywhere is the guide's example. If that example is real arithmetic at the catalog's USD 0.15/0.60 per million for `gpt-oss-120b` (last checked in our 12 October entries), the token cost is USD 0.00045 and the remainder, about **USD 0.0516 per request**, would be the fee [independently verified arithmetic on a possibly illustrative example — the fee itself remains **unknown**]. For scale, Brave's published search price is USD 5 per 1,000 requests (USD 0.005), Exa direct is USD 4–7 per 1,000; the implied Tinfoil fee would be roughly ten times Brave per request, charged per request rather than per search. The privacy filter fee (`other_cost_usd`) is likewise unpublished. The honest way to learn the fee is one metered synthetic request with the metrics header, or a supplier answer.

**Addendum, 22 October [supplier statement]:** the supplier's reply of 22 October states the web search fee is **USD 0.05 per request**, listed at https://tinfoil.sh/pricing#api, and that web search "works with all chat models". This matches the example arithmetic above. The agent's text fetch of the pricing page the same day showed no API table, so the figure stands as a supplier statement until read from the rendered page or observed in a metered `cost_usd`. The harness in `evaluation/enclave-search-harness.ts` carries it as the fee floor: at most three requests means at least USD 0.15 in fees plus tokens, and a permit cap below that floor is refused.

## Recommendation

**Proceed to a bounded synthetic test after the 23 October decision**, contingent on Tinfoil remaining the inference direction under the existing decision sequence; if the owner selects Privatemode or the narrower public-only scope without Tinfoil, this candidate lapses with that choice and should be recorded as rejected by consequence.

Reasons. (1) It is the only documented option that removes the backend-to-provider plaintext query path, which is the privacy defect of the current research design that no Brave plan would cure. (2) The published Tinfoil terms contain no identified obstacle to temporary-session display or user-initiated Copy answer, which is all the current boundary needs; saved history stays closed either way. (3) The two facts that decide viability — the per-request fee and whether the deployed release and our account actually serve the feature — cannot be learned from publications and the supplier has not answered commercial questions; one metered synthetic request answers both at a cost bounded by the existing authorization. (4) The product cost is a change in kind: the user loses pre-send query approval. That is a founder decision, not an engineering one, and the test should produce the concrete query-disclosure evidence (what the model searched for, how often, what masking did) the founder needs to make it.

Preconditions for the test, none of which are met yet: owner approval of the test scope and of the per-turn capability disclosure for the test only; a fresh exact-digest development permit against the then-current router release with the usual negative checks; `pii_check_options` and `prompt_injection_check_options` present; `search_context_size: "low"`, `filters.allowed_domains` limited to a few named public hosts, no `previous_response_id`; a public synthetic query with no private data; the first request sent alone with `X-Tinfoil-Request-Usage-Metrics: true` and the trailer recorded before any second request; at most three requests; no retries; results, replies and queries kept in the temporary session and only counters, hashes and the metrics line written to the durable record; no production allowlist, qualification record, account setting or privacy copy changed. Record the actual `cost_usd` and `web_search_calls` and refresh billing before and after.

What would flip this to reject: a measured fee that makes research unaffordable against the USD 5 authorization pattern, a supplier answer that excludes customer retention of titles and URLs, the founder declining post-hoc query disclosure as the product model, or the deployed enclave not serving the feature for a non-experimental model.
