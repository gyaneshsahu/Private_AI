# PrivateAI readiness checklist

## Relay guards: qualified-model header, one request per account, completed-request metering — 22 October

Launch plan item 1.1, implemented locally and not deployed. These are the controls the relay can enforce itself whatever the supplier answers; they do not close a qualification gate and do not change what the supplier retains.

- **Model allowlist.** The relay now sends `X-Tinfoil-Model: <qualified model>` on every forwarded request; the supplier's proxy guide states the enclave checks this header against the encrypted body and rejects a mismatch. A client that sends a different `X-Tinfoil-Model` is refused with 400 before any forwarding; the client header is never trusted or forwarded.
- **One request in flight per signed-in account**, enforced locally before shared admission, in addition to the existing global bound of three. This follows the supplier's own advice that a hard ceiling must come from bounded concurrency because spending caps are soft. It does not bound output length or money per request; `max_completion_tokens` stays inside the encrypted body.
- **Completed-request metering.** The relay requests `X-Tinfoil-Request-Usage-Metrics: true` and, after a stream ends, reads `X-Tinfoil-Usage-Metrics` from the HTTP trailer (or the header for non-streaming replies). This required switching the upstream call from `fetch` to `undici.request`, since WHATWG fetch exposes no trailers (21 October proof-of-concept). Parsed prompt and completion tokens, model, published `cost_usd` and web-search call count are stored per request ID with the `transport_complete` settlement in a new `usage_metrics` table (SQLite ledger, and PostgreSQL migration `0013-usage-metrics.sql`). Interrupted, cancelled or uncertain requests record no metering, by design: the provider bills them but gives the relay nothing to reconcile, which stays an open supplier question. Request counts remain the admission unit; the account page does not yet show tokens or cost.
- **Operator upgrade command.** `node --import tsx server/deployment-database-entry.ts apply-pending /etc/secrets/render-config.json` applies only unrecorded migrations under the advisory lock and refuses mismatched checksums; startup still never migrates. **Any candidate at or after this commit needs that one-time command run once against the hosted database before deployment, or readiness stays 503.** The live `4eb86b1` and the pending candidate `9c9be8e` are unaffected.
- **Privacy note.** The relay now learns per-request token counts and model per account, never content. This is recorded here for the owner's privacy text (plan item 1.4).
