# PrivateAI readiness checklist
## Qualified fallback model with explicit user confirmation — 22 October

Launch plan item 1.3, implemented locally, not deployed. Background: the supplier's 22 October mailing states catalog models can be swapped or deprecated at any time, and the changelog shows a model removed within a month of being added. The qualified model stays a value in the qualification report; this change adds an optional second name and an honest path to it.

- **Report.** `fallbackModel` is an optional field of the qualification report; it must differ from `model` and may not be `auto`. It names a second catalog model on the same qualified deployment and inherits the same review evidence; it is not a second qualification. Model-specific reasoning toggles stay bound to the usual model and are not applied to the fallback.
- **Relay.** The relay accepts the client's `X-Tinfoil-Model` header only when it names the usual or the fallback model, forwards that choice, and otherwise still pins the usual model. When the enclave refuses a request (any 4xx, which the supplier states is not billed), the relay now answers 502 with `X-PrivateAI-Upstream: rejected`; other failures carry `unavailable`. Only that class is exposed; upstream status text and bodies are never reflected.
- **Client.** The browser sends its chosen model in the header so the enclave check and the relay allowlist agree with the encrypted body. A rejected request surfaces as the new `HTTP_UPSTREAM_REJECTED` failure with the message "The protected service did not accept this request; nothing was run or billed." If a fallback model is qualified, the app then asks, in a confirmation dialog, whether to answer with the fallback model, naming both models; cancelling leaves the question unanswered. The fallback is a separate, explicitly confirmed request, never an automatic retry, which keeps the existing no-retry rule. A reply produced this way carries a visible note, "Answered by the fallback model …", saved with the conversation.
- **Not changed.** No fallback is named in any report today; the development default remains the single provisional model. Naming one is an owner decision that requires the same qualification evidence for the second model's worker repository and digests. Switching models is never silent.

Tests: qualification validation accepts a distinct fallback and refuses identical, automatic or empty names; relay forwards the fallback header, refuses a third model, and classifies 404 as rejected and 503 as unavailable without leaking upstream text; completion events classify a rejected 502; the real-browser transport test's new `rejected` scenario shows the client message without the relay's error body. Validation on this machine: typecheck and build pass; `npm test` 520 passed / 0 failed / 149 skipped across 131 files; `npm run test:e2e` 56 passed. Exact-commit CI still required.


## On-device identifier masking before encryption — 22 October

Launch plan item 1.2, implemented locally, not deployed. Owner approved the narrower privacy claim on 22 October: "ID numbers, bank and contact details stay on your device; everything else is sealed." The implementation matches that claim and nothing wider.

**What it does.** `src/identifier-masking.ts` runs in the browser as the last step before encryption. In every outbound message, including attached document text and earlier replies in the context, it replaces recognised identifiers with placeholders such as `{{IBAN-1}}` and keeps the originals in memory on the device. One instruction is appended to the system prompt telling the model to copy placeholders unchanged. The streamed reply has the originals put back on the device, with a hold-back so a placeholder split across two chunks is never shown half-restored. Each reply records a plain-language note shown under the answer, for example "Kept on this device: 1 bank account, 1 phone number", and that note is saved with the conversation.

**What is recognised, each with a check that limits false positives:** IBANs (mod-97), payment card numbers (Luhn, 13 to 19 digits), German tax IDs (11 digits with the ISO 7064 check digit and repeated-digit rule) and formatted Steuernummern, German pension insurance numbers (embedded birth date plausibility), passport or ID document numbers only when a document label precedes them, email addresses, phone numbers starting with +, 00 or 0 with 8 to 15 digits, and dates only when a birth label precedes them. Not recognised, by design and stated in the module: names, postal addresses, employers and any free-text fact. The product and website copy must not claim more than this list.

**Boundaries.** The sealed server still receives the rest of the question, so the server-side promise is unchanged: encrypted in transit, processed inside the enclave, not retained beyond the provider's documented volatile cache. Research queries sent to the search provider through our backend are not masked by this change; the user still approves that query verbatim, and masking it is a separate decision for Phase 4. The same value is always mapped to the same placeholder within one request, and nothing about the masking is sent to our relay.

**Tests.** Unit: check-digit validators, detection of each kind in mixed German text with money, dates, counts and an emergency number left untouched, labelled-only passport and birth-date detection, stable placeholders, restoration including unknown placeholders left alone, the kept-on-device note wording, and streamed reinsertion across chunk boundaries. End to end: a new `masked` scenario in the real-browser transport test sends a message containing an IBAN and a phone number through the actual verifier, EHBP encryption and relay; the decrypted wire payload contains the placeholders and the system instruction and neither value, the fake enclave answers with a placeholder split across two frames, and the displayed answer carries both original values with the kept summary reported. Validation on this machine: typecheck and build pass; `npm test` 517 passed / 0 failed / 149 skipped across 130 files; `npm run test:e2e` 56 passed. Exact-commit CI still required.

## Relay guards: qualified-model header, one request per account, completed-request metering — 22 October

Launch plan item 1.1, implemented locally and not deployed. These are the controls the relay can enforce itself whatever the supplier answers; they do not close a qualification gate and do not change what the supplier retains.

- **Model allowlist.** The relay now sends `X-Tinfoil-Model: <qualified model>` on every forwarded request; the supplier's proxy guide states the enclave checks this header against the encrypted body and rejects a mismatch. A client that sends a different `X-Tinfoil-Model` is refused with 400 before any forwarding; the client header is never trusted or forwarded.
- **One request in flight per signed-in account**, enforced locally before shared admission, in addition to the existing global bound of three. This follows the supplier's own advice that a hard ceiling must come from bounded concurrency because spending caps are soft. It does not bound output length or money per request; `max_completion_tokens` stays inside the encrypted body.
- **Completed-request metering.** The relay requests `X-Tinfoil-Request-Usage-Metrics: true` and, after a stream ends, reads `X-Tinfoil-Usage-Metrics` from the HTTP trailer (or the header for non-streaming replies). This required switching the upstream call from `fetch` to `undici.request`, since WHATWG fetch exposes no trailers (21 October proof-of-concept). Parsed prompt and completion tokens, model, published `cost_usd` and web-search call count are stored per request ID with the `transport_complete` settlement in a new `usage_metrics` table (SQLite ledger, and PostgreSQL migration `0013-usage-metrics.sql`). Interrupted, cancelled or uncertain requests record no metering, by design: the provider bills them but gives the relay nothing to reconcile, which stays an open supplier question. Request counts remain the admission unit; the account page does not yet show tokens or cost.
- **Operator upgrade command.** `node --import tsx server/deployment-database-entry.ts apply-pending /etc/secrets/render-config.json` applies only unrecorded migrations under the advisory lock and refuses mismatched checksums; startup still never migrates. **Any candidate at or after this commit needs that one-time command run once against the hosted database before deployment, or readiness stays 503.** The live `4eb86b1` and the pending candidate `9c9be8e` are unaffected.
- **Privacy note.** The relay now learns per-request token counts and model per account, never content. This is recorded here for the owner's privacy text (plan item 1.4).

Tests: relay refuses a foreign model header and sets both headers on every forward; a trailer is parsed and stored, an uncertain outcome stores nothing, idempotent settlement keeps the first metering, malformed metering is rejected; one-per-account concurrency through real HTTP with the SQLite and PostgreSQL ledgers; header parser unit cases; migration count 13. Validation on this machine: typecheck and build pass; `npm test` 513 passed / 0 failed / 149 skipped across 129 files; `npm run test:e2e` 56 passed; `npm run test:durable` 122 passed, zero skipped, against a throwaway postgres:17 container; the PostgreSQL-gated account-usage, migrations (13 applied), restore and ledger suites 12/12. One retained environment note: the first durable attempt failed only because Docker Desktop had stopped; restarted and rerun. Exact-commit CI still required.
