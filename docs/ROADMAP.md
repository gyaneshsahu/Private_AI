### Scope and modality decisions

Launch targets everyday writing/chat, history/context, local documents, source-grounded research, reasoning, conversational coding, mobile use, accounts, subscriptions/usage, recovery and support. Competitive usefulness is measured, not claimed from catalog marketing. Coding initially means explanation/debugging/generation; remote execution of arbitrary user code is a separate sandbox/security feature, not implied.

**General image understanding:** launch candidate in M4, not the existing OCR feature relabelled. Requires privacy-qualified vision deployment, image/text grounding and adversarial-image tests, size/cost bounds and accessible descriptions. **Voice:** assess local transcription first; propose deferring conversational voice at initial public opening unless device performance and confidential transcription/TTS qualify during M4. Browser SpeechRecognition can send audio to a service and is not a private shortcut ([MDN](https://developer.mozilla.org/en-US/docs/Web/API/SpeechRecognition)). **Image creation/editing:** assess in M4 but propose deferral from initial opening: no integrated qualified generation/editing path, retention evidence, editing fidelity or abuse controls currently exist. Both proposals need explicit founder scope review before the release promise is finalized. Neither is removed from the full-product roadmap or allowed to use an ordinary API silently.

**Calculator time box:** at most one further architecture/compatibility batch before the next roadmap decision, bounded to one engineering session and a predeclared synthetic request budget. Investigate constrained argument generation, not more example-specific rules. If it does not improve complete-answer delivery and latency, retain the explicit deterministic calculator and normal-answer development baseline, keep automatic calculation experimental, and advance M2/M4. This does not waive numerical correctness at release.

### Architecture decisions and critical path

Recommended deployment is a modular monolith: React client + Node account/research/opaque-relay service + PostgreSQL for identity, sessions, entitlements and content-free usage. Start one service instance; no Kubernetes, autonomous agent framework, custom GPU cluster or microservices without measured need. PostgreSQL is a proposed production dependency, not provisioned here. Existing SQLite remains the development/restricted-service adapter until migration/rollback tests pass. Keep private content browser-side; optional ciphertext sync is a separately reviewed addition, never plaintext server history. See ARCHITECTURE for trust boundaries and alternatives.

Critical dependency path: qualify browser→worker/GPU/retention **and** demonstrate useful/safe complete conversations; implement durable account/admission/billing; complete research/document and mobile workflows; verify operations and human acceptance; limited-user release check; founder public-launch decision. There is useful independent work before provider decisions. No amount of UI progress closes a privacy blocker.

Maintained-service choices: evaluate Better Auth as the TypeScript/PostgreSQL authentication default rather than extend custom credentials; verify pinned version, advisories, account-linking and recovery behavior before adoption ([security](https://better-auth.com/docs/reference/security), [installation](https://better-auth.com/docs/installation)). Prefer Stripe-hosted Checkout/Portal plus signed, idempotent subscription webhooks over custom payments ([webhooks](https://docs.stripe.com/billing/subscriptions/webhooks), [portal](https://docs.stripe.com/customer-management)). Render remains a viable initial host; persistent-disk attachment is single-instance infrastructure, not the production shared state design ([disk constraints](https://render.com/docs/disks)). No new service, plan, secret or payment is activated by this recommendation. Costs need the actual plan, workload and owner approval at provisioning; do not invent a fixed hosting estimate.
