# Canvas (14 November 2026)

Owner's request: "side panel with editable document/table/mini page, with export to PDF", as in ChatGPT Canvas and Claude Artifacts, scaled to what is safe here. Checklist row U7.

Status: built and tested offline, switched off by default. Nothing verified live.

## What it is

- One editable document per conversation, in a panel beside the chat.
- Created only by the user: "Open in canvas" under any completed answer copies that answer into the canvas. No model protocol change, no extra request, no tool call.
- If the conversation already has a canvas with other text, the app asks first. OK replaces it (the old text goes to the undo list). Cancel opens the canvas as it is. This is also the way back to a closed canvas.
- Views: Edit (a plain Markdown text box), Preview (the same renderer as answers: tables, maths, code, links; images show as their alt text, raw HTML is not rendered), and Table when the whole text is one Markdown table.
- Table view: a grid of text fields. Add row, add column, remove the row or column of the last selected cell. Pasting cells from a spreadsheet (tab-separated, quoted cells allowed) into any cell writes them from there and grows the table. Every change writes the Markdown table back.
- "Ask for changes": the user types what should change. The app sends ONE ordinary message through the existing send path (masking, allowance, stop switch, answer modes, context budget): the request, a short note, then the canvas text once. The cost shows on the button before sending ("uses 1 request" in Fast, 5 in Thinking, as for any message). The answer appears in the chat as usual and in the panel as "Proposed changes" with a preview. The canvas changes only on Apply. Discard leaves it as it was. If the answer did not arrive completely, the panel says so and offers Dismiss.
- Earlier change requests and their answers are taken out of the context (the ordinary "included" mark, visible in the context review), so the canvas text is sent once per request and not again with every later change.
- Undo: the version before each Apply (and before a replace by "Open in canvas") is kept, up to 20 versions, in memory only. Typing has the text box's own undo.
- Exports: Copy as Markdown, Download .md, Download .csv (tables only), Export canvas as PDF (the existing print path, the canvas alone: title and text, no message headings). "Remove canvas" deletes it from the conversation after a confirmation.

## What it is not

- Not model-driven. The model cannot open, write or edit a canvas by itself. A model-driven canvas would need: a tool or output format the model uses to say "this is a canvas document" (for example a `canvas` tool call with the full text, or a fenced block with a reserved name), a parser that refuses malformed output, a rule for when the model may create one (every answer would otherwise become a canvas), a cost rule for the extra output, and testing with Privatemode's models that they follow it reliably in German and English. Not built.
- No HTML mini pages (see below).
- No rich text editor (no contentEditable), no new dependency, no Word, Excel or PowerPoint export.
- One canvas per conversation, not several.
- No partial edits: the model rewrites the whole document. Long documents cost more output tokens and take longer.

## HTML mini pages: left out

The owner prefers no feature over an unsafe one. A preview of model-written HTML was analysed and not built:

- Without scripts (`sandbox=""`, inner CSP `default-src 'none'`), a page cannot run code, fetch, open windows, submit forms or navigate the top page. But such a page is only static HTML and CSS, which the Markdown preview already covers in a safer form. A link the user clicks inside the frame could still load an outside page in the frame unless the app's own CSP blocks it.
- With scripts (`sandbox="allow-scripts"` without `allow-same-origin`, srcdoc, inner CSP with `connect-src 'none'`), the parent page, cookies and storage are out of reach. But the network is not reliably closed: Chromium does not apply CSP to WebRTC, so a script can send data out through a STUN or TURN server (`RTCPeerConnection`), and DNS prefetching of link names is another known leak. The canvas text may hold personal data the user typed, so a leak would break the product's core promise. The only clean answer is serving the frame from a separate, sandboxed origin with its own strict headers, or a WebRTC block that browsers do not offer to pages today.

So: no iframe, no change to the app's content security policy (`frame-src` and `child-src` stay as they are), no hostile-page test. If the owner wants mini pages later, the honest route is a separate origin (its own domain, `Content-Security-Policy: default-src 'none'; script-src 'unsafe-inline'; style-src 'unsafe-inline'; sandbox allow-scripts`), plus a browser test that a hostile page cannot reach the parent, fetch, load images, open sockets or WebRTC, post forms, navigate the top page, open windows or read storage.

## Limits

| Limit | Value | Why |
| --- | --- | --- |
| Canvas text | 18,000 characters | With the request (1,500) and the note, one change request stays inside the 20,000 character message limit. Longer text is refused with a plain message (the text box also stops there). "Open in canvas" refuses a longer answer. |
| Request | 1,500 characters | Same reason. |
| Table | 200 rows, 30 columns | Keeps the grid usable on a phone; a bigger paste is refused. |
| Undo | 20 versions | In memory only, per conversation, gone on reload. |
| Context | the model's input limit | The ordinary context check applies; a request that does not fit is refused before sending. |

CSV export: comma separated, CRLF, quotes doubled (RFC 4180), with a UTF-8 byte order mark so spreadsheet programs read umlauts. A cell that a spreadsheet would run as a formula (starting with `=`, `@`, `+` or `-`, except plain numbers such as `-5` or `+3,50`) gets a leading apostrophe, so a table a model wrote cannot run anything when opened.

## Saving and privacy

- The canvas is part of the conversation object (`canvas: { text, resolved? }`). It is saved with the conversation in the encrypted vault on the device when the conversation is saved, and is part of backup and restore through the same schema. Conversations saved before this have no canvas and stay readable. Over the limit or with unknown fields a saved canvas is refused like any malformed saved conversation.
- Never on the server. Incognito and unsaved chats keep it in memory only.
- It leaves the device only inside a change request the user sends, masked like any message, to Privatemode's confidential models.
- `resolved` holds only the id of the answer that was applied or discarded.
- No privacy wording draft: no user-facing statement changes. The canvas is conversation content, stored and sent as conversation content already is.

## The switch

Build setting `VITE_CANVAS=1` (src/device-features.ts), off by default. Nothing on the server, so no `inference.*` field, no status field and no `PRIVATEAI_*` switch. Off: no "Open in canvas" button and no panel; a saved canvas stays in the vault untouched.

## Layout and access

- From 1100 px: a panel on the right (38 percent of the width, 380 to 620 px), the conversation and composer narrow beside it and keep working, including "Jump to latest" (the composer is tested beside the panel; the jump button is not tested separately). Close with × or Escape.
- Below 1100 px (tablet and phone): a full-screen sheet with "← Back to chat"; the page behind is inert (no focus, no clicks) while it is open.
- A labelled region (`aside`, named by its heading "Canvas"). Focus moves to the heading on open and returns to the button that opened it on close. View buttons use `aria-pressed`. Every table cell has a name ("Row 2, column 3"). Buttons are at least 44 px high below 1100 px. No horizontal page scroll; a wide table scrolls inside its own box.

## Tests

- `tests/canvas.test.ts` (8 tests): table to grid and back (escaped pipes, empty cells, short and long rows, alignment), not-a-table cases, TSV paste with quotes, tabs and line breaks inside cells, paste growing the table and the table limits, CSV with quotes, commas, padding and formula cells, the change request (canvas once, instruction first, no digits in the note, every refusal), earlier requests left out of the context and the context check, proposals with apply, discard, a failed answer and undo order and limit, the saved round trip with old data and oversize refusal, the switch.
- `tests/canvas-ui.test.ts` (6 tests, real headless Chromium at 375, 768 and 1280 px in English and German): open from an answer, focus on the heading, side panel vs full-screen sheet and inert page, composer still usable beside it on desktop, edit and preview, ask for changes with the cost on the button and exactly one request in which an email address is masked and the canvas marker appears once (the real `src/verified-chat.ts` masking; only attestation and transport are stand-ins), the canvas unchanged until Apply, Apply and Undo, the table grid with typing spaces, a spreadsheet paste and add row, the CSV file's exact content, Copy as Markdown, Download .md, the PDF print view with the canvas alone, Escape closing with focus returned, Cancel on replace keeping the canvas, no sideways scroll, target sizes, no request leaving the machine.

## Not verified

- Anything with Privatemode: whether the models reliably return the whole revised document without an introduction, in the document's language, how long a rewrite of 18,000 characters takes, real token use.
- A real phone and tablet (on-screen keyboard over the text box, paste from a phone spreadsheet app), Safari and Firefox, a screen reader.
- The saved round trip through the real vault UI (covered by the schema test only), backup and restore by hand.
- Printing to PDF in a real browser dialog (the print view is tested; the dialog is not).
