# Image upload and understanding (a question about a picture), 14 November 2026

Status: **built and tested offline. Switched off by default. Nothing was verified live.** No call was made to Privatemode, no key was read, no real photo, document or phone was used.

## What it does

The user opens "Attachments and tools", chooses "Ask about a picture", takes a photo or picks a PNG or JPEG, covers private parts with black boxes, checks the exact picture, and attaches it. Then the user types a question and presses Send. The picture goes with that one message to the model. The answer comes back as usual. After that the picture is gone. The chat keeps the question, the answer and the line "[Picture: not kept]".

## What the lead verified live on 14 November (not by this agent)

Privatemode's model list gives `glm-5.3-flash` the tasks generate, tool_calling and vision. `glm-5.3` (Thinking) has no vision. So only the Fast model can read a picture.

## The privacy layers, and the limit of each

| # | Layer | What the code does | Its limit |
| --- | --- | --- | --- |
| 1 | No hidden file data | The chosen file is decoded and drawn into a fresh canvas (the existing photo dialog, `src/photo-capture.ts`). Only pixels are encoded again. EXIF, GPS, comments and text chunks cannot survive. The JPEG that is sent is then stripped of every application segment except the plain JFIF header (`stripJpegMetadata`), so the browser's own colour profile is gone too. If any such segment is still found, nothing is sent | What the picture shows stays: a street sign, a screen, a reflection |
| 2 | Black boxes by hand | The user drags on the picture (mouse or finger) or adds a box and moves it with the arrow keys. Undo and "Remove all boxes". The boxes are filled into the pixels before encoding. They are not an overlay. The user then sees the encoded picture itself and attaches exactly that | The user must see the private part and cover it. A box that is too small leaves letters visible at its edge |
| 3 | Suggested boxes | Only when the user presses "Suggest boxes": the on-device OCR (German and English data) reads the words, the masking rules for typed text run on them (`findIdentifiers`: email, phone, IBAN, card, tax, insurance and ID numbers, dates of birth), and each match becomes a black box, one per line, a little larger than the words. The user removes boxes or adds more | Only as good as the OCR. A misread digit means no match and no box (tested). Names and addresses are not found: the rules do not look for them. Handwriting, small or skewed text, text in a photo of a scene: often missed. The text after every run says that suggestions can miss things |
| 4 | Faces | Offered only where the browser has its own on-device face finder (the Shape Detection API, `FaceDetector`). Then "Cover faces" puts a black box over each face found. Everywhere else there is no button, and the text says: draw a box over each face | **No blur was built, and no face finder was added.** `FaceDetector` exists in very few browsers (in Chrome mostly behind a flag). So for almost every user this layer is "draw the box yourself". The black box is stronger than a blur, which can sometimes be undone. The path was tested with a stand-in face finder only |
| 5 | Never stored | The picture is one value in the app's memory (`attachedImage` in `src/App.tsx`). It is never put into the conversation object. The message gets a flag `image: true` and nothing else. The saved format has no field that could hold a picture, and the vault refuses to save a conversation that carries a base64 picture anywhere (`containsImageData`). On the server the encrypted body lives in memory for the one request, as for chat. Nothing is logged | The model provider processes the picture. Privatemode says it does not keep chat content. We have nothing in writing about pictures (live check 11). The browser's memory holds the picture until the answer ends or the user removes it |
| 6 | First-upload notice | Before the first picture, in English or German: the picture goes to the protected Fast model, suggestions can miss things, faces, handwriting and anything else in the picture are not covered unless the user covers them, the picture is not stored. A test fails if the texts claim that everything private is found | A notice is read once. The same limits are repeated in the tool |
| 7 | Health pictures | See "The health rule" below | The app cannot know what a picture shows. It relies on the user's answer |

**One sentence in the privacy copy stops being true once this is on:** "ID, bank and contact details stay on your device". A number inside a picture is sent unless the user covers it. The wording draft is `docs/images-privacy-wording-draft-20261114.md`.

### The health rule

Today, for text, the consent card is shown once before the first message, and only while the server sets `healthConsentDraft` (off in production). For a picture the app cannot read the content. The rule chosen:

- Consent step on, and the user has agreed: no extra question.
- Consent step on, and the user has not agreed (never asked, or said "Not now"): **every picture is asked about** after it is chosen: "Does this picture show health or other sensitive details?" "No" continues. "Yes" shows the existing consent card, unchanged. "I agree" continues. "Not now" discards the picture, and nothing is sent.
- Consent step off: nothing is asked. The picture flow adds no consent of its own.

Why: a user who declined for text can still send text and is asked to leave health details out. A picture of a medical letter cannot "leave it out", so the question is asked each time. The text flow is not changed in any way.

## Routing

- A picture question always goes to the Fast model, whatever mode is selected. The relay refuses a declared image request in any other mode or on any other model.
- The answer label says "Fast (pictures are read by the Fast model)".
- If the user chose Thinking, the check step says before attaching: "You chose Thinking. Pictures are read by the Fast model, so this answer comes from Fast."
- No backup retry for a picture question: a backup model may not read pictures.
- No search step: a message with a picture goes straight to the model.
- Follow-up messages do not resend the picture. The model is told in plain words that a picture was attached and cannot be seen now. To ask again about the picture, the user attaches it again. The composer note says so.
- "Answer again" on a picture question asks without the picture, for the same reason.

## The two switches (both off by default)

1. Deployment config: `inference.images`

   ```json
   "images": { "enabled": true, "maxBytes": 280000, "dailyImages": 10 }
   ```

   | Field | Range | Meaning |
   | --- | --- | --- |
   | `enabled` | true or false | The switch. Absent or false: no menu entry, and a declared image request is refused |
   | `maxBytes` | 50,000 to 290,000 | Largest JPEG the browser sends. It sizes the larger body bound at the relay |
   | `dailyImages` | 1 to 100 | Picture questions per account in any 24 hours |

2. Qualification report: `vision`

   ```json
   "vision": { "model": "glm-5.3-flash", "allowanceCost": 2 }
   ```

   The model must be the Fast mode's own model (or the report's model when it has no modes). So the relay already admits it, and the daily model check already watches it: the recorded baseline holds its `vision` task, and the check alerts if that task disappears. `allowanceCost` must not be lower than a Fast message's cost. Only a Privatemode report may carry `vision`.

`GET /api/status` then carries `images: { "maxBytes": 280000 }`. The browser shows the menu entry only when that field is present. It is absent when the switch is off, when the report has no `vision`, when chat is paused and when the spending limit is reached.

On the development server (`server/index.ts`) the switch is `PRIVATEAI_IMAGES=1` (280,000 bytes, 10 a day). The report still needs `vision`.

**Content-part format (not verified live):** the latest user message becomes

```json
{ "role": "user", "content": [
  { "type": "text", "text": "the masked question" },
  { "type": "image_url", "image_url": { "url": "data:image/jpeg;base64,..." } }

```

Offline evidence only: the SDK's Wasm contains the paths `#.content.#.image_url` and `#.content.#.image_url.url`, so it knows this shape. The owner's notes have no "Vision input" section text, only the page title in the list. This is live check 1.

The question's typed text is masked as always. Masking works on text. Nothing inside the picture is masked by it.

## Admission at the relay

The body is encrypted. The relay cannot see a picture. So the browser declares it with the header `x-privateai-kind: image`, like the answer mode in `x-privateai-mode`. One declaration does three things together:

1. The body bound becomes the text bound plus the image allowance (below).
2. The request costs `vision.allowanceCost` units, not the mode's text cost.
3. It uses one of the account's picture questions for the day.

Without the declaration the text bound applies, so a large body is refused (413). A modified browser cannot get the larger bound at the text price. Any other value of the header, or the header while pictures are off, is refused (400). A declared request must name the vision model and the Fast mode (400 otherwise).

Everything else is the chat route unchanged: session and CSRF, stop switch, three per instance, one per account, spend guard, the daily unit cap, the allowance ledger. A text message's retry credit never pays for a picture question. A picture question the provider refuses can be sent again within a minute without a second charge, and its day count is given back. A refusal before anything was forwarded (allowance, spend, daily cap) does not use up one of the day's pictures.

The render bridge forwards `x-privateai-kind` (`server/render-bridge.ts`). The header is not passed on to Privatemode.

Counts (names only): every outcome of a picture question is counted a second time under `image.*` beside its `chat.fast.*` count: `image.completed`, `image.interrupted`, `image.refused_size`, `image.refused_image_daily`, `image.refused_allowance`, `image.refused_daily`, `image.refused_spend`, `image.refused_account_busy`, `image.refused_instance_busy`, `image.upstream_rejected`, `image.upstream_unavailable`, `image.upstream_model-not-found`, `image.status_400`, and `image.refused_off`, `image.refused_kind` for a declaration that was not accepted.

## Caps, with the arithmetic

**Longest edge: 1,568 pixels** (`IMAGE_MAX_EDGE`). Larger pictures are scaled down on the device, never up. This is a common upper size in vision-model guidance. It was not checked against GLM-5.3-Flash (live check 3).

**One picture per message.**

**Byte cap: `maxBytes`, proposed 280,000.** The browser encodes a JPEG and tries, in this order, quality 0.85, 0.70, 0.55 at full size, then the same three at 80%, 64%, 50%, 40% and 30% of the size. The first result at or under the cap is used. If none fits, the picture is refused with the advice to crop. A test shows a "0.4 bytes per pixel" picture of 1,568 by 1,176 landing at 1,254 by 940, quality 0.55.

**Why 280,000:** it must fit the Render bridge's request limit of 1,048,576 bytes together with a full text message.

```
JPEG                                   280,000 bytes
as base64 data URL: 23 + 93,334 x 4  = 373,359 characters
x 2 (worst case for the encryption)  = 746,718
+ 1,024 (JSON around the part)       = 747,742   the image allowance
+ text bound: 32,000 characters x 8  = 256,000
                                     = 1,003,742 bytes   the bound for a declared image request
bridge limit                         = 1,048,576         44,834 bytes to spare
```

At the top of the range, 290,000 bytes, the sum is 1,030,406. Above that the config is refused. The bound never exceeds 1,048,576, also for a report with a larger text bound.

**The factor 2 is a guess on the safe side.** How much the SDK's encryption enlarges a body was not measured. If it is close to 1, the same arithmetic would allow a JPEG of about 580,000 bytes, and the range in the config can be raised. If it is above 2, full-size pictures are refused as too large (413). This is live check 4.

**Is 280,000 bytes enough?** General knowledge, not measured here: a screenshot or a scanned page at 1,568 pixels is usually 100 to 300 KB as JPEG. A detailed photo is 250 to 500 KB at quality 0.85, so photos will often be sent at lower quality or at 1,254 pixels. Small print in a photo may suffer. The user sees the exact result before attaching.

**Picture questions per day:** `dailyImages`, proposed 10, or 5 while tokens are short (see cost).

**Allowance:** `vision.allowanceCost`, proposed 2 (a Fast message is 1, Thinking is 5). The daily unit cap and the period limit apply to these units.

**What a modified browser could do.** It can declare an image request and fill the larger body with text. By the relay's own measure of 8 bytes per character that is about 125,000 characters instead of 32,000, for the image price, at most `dailyImages` times a day. At the owner-reported Fast input price that is at most about EUR 0.025 per request, EUR 0.25 per account per day at 10 a day.

**Shortcuts to know:**

- The spend guard counts every request at "one token per allowed input character". A picture's tokens are not in that worst case, and neither is the oversized text above. Until live check 3 gives the token count of a picture, the spend guard can undercount a picture question. The money is small (see cost), but the guard is not exact for pictures.
- The day count and the retry credit live in the server's memory. A restart forgets them. The allowance units are in the durable ledger.

## Cost

Prices are **owner-reported** (`docs/privatemode-master-notes.md`), not verified by us: GLM-5.3-Flash EUR 0.20 per million input tokens, EUR 0.65 per million output tokens, before 19% VAT.

**How many tokens a picture counts is not known.** The table assumes 3,000 tokens for a picture at the largest size, 2,000 tokens for the instructions and the question, and 500 tokens of answer. These are assumptions until live check 3.

| | Questions | Tokens | Cost |
| --- | ---: | ---: | ---: |
| One picture question | 1 | 5,500 | EUR 0.0013 |
| One account, one day at 10 | 10 | 55,000 | EUR 0.013 |
| 30 invitees, one day, all at 10 | 300 | 1,650,000 | EUR 0.40 |
| 30 invitees, 30 days, all at 10 | 9,000 | 49,500,000 | EUR 12 |
| The same at 5 a day | 4,500 | 24,750,000 | EUR 6 |

**The token quota is the tighter limit, not the money.** The owner reported 1.579M of 5M free tokens left on 13 November, and pay-as-you-go cannot be switched on yet (checklist rows K6 and P12). 30 invitees at 10 pictures each would use about that much in one day. So pictures should stay off until pay-as-you-go works, or start with a small `dailyImages`.

`deepseek-ocr-2` (an OCR model in the owner's notes, EUR 0.77 in and 1.27 out per million) is not used. The on-device OCR needs no provider call.

## What is switched off by default, and what changes for everyone

Off by default: everything a user can see. Without `inference.images.enabled: true` and `vision` in the report there is no menu entry, no status field, and a declared image request is refused.

Live for everyone once this code is deployed, with the switch off:

- The render bridge forwards one more header, `x-privateai-kind`.
- The vault refuses to save a conversation in which some value is a base64 picture (`data:image/...;base64,`). No code path puts one there. A user who pastes such a data URL as the whole text of a message would get "pictures are never stored" instead of a save. This is unlikely, and the owner should know it.
- A saved message may carry `image: true`. Older code that reads such a save drops the flag and shows the question without the "[Picture: not kept]" line.
- The photo dialog (`src/PhotoCapture.tsx`) no longer listens to the dialog element's own `close` event. In the development build, React mounts every component twice, and that event closed the dialog the moment it opened (seen in a test here, for "Photo to text" too). Escape and the close button work as before. `tests/browser/photo-to-text.spec.ts` covers Escape and was not run.
- The photo dialog takes optional other words (`wording`). "Photo to text" passes none and reads as before.

## What the lead must check live

Nothing below was checked. The probe script is `evaluation/privatemode/image-probe.ts` (it needs the key and bills a fraction of a cent per call).

1. **Content-part format.** Run the probe with no arguments. It builds a small PNG (a red square and a blue bar on white) and asks for a description. A reply that names the shapes and colours confirms the format. A 400 means the format or the model is wrong.
2. **One synthetic picture question on `glm-5.3-flash`.** The same run. Also run once with `--model glm-5.3` to see what the Thinking model does with a picture (refusal, or an answer that cannot see it).
3. **Token count.** The probe prints `promptTokensForThePicture` (prompt tokens with the picture minus without). Run it with a JPEG at 1,568 pixels on the long edge and with a small one. Put the numbers into the cost table, and decide whether the spend guard needs a picture term.
4. **Size limits.** (a) Directly: run the probe with JPEGs of about 100 KB, 280 KB, 1 MB and 5 MB to learn Privatemode's own limit. (b) Through the app (development server, `PRIVATEAI_IMAGES=1`, `vision` in the report): attach a picture that comes out near 280 KB, and read the size of the request to `/v1/chat/completions` in the network panel. It must be at most 1,003,742 bytes. Divide by the data URL length to get the real encryption factor.
5. **A picture with German text.** A screenshot of a made-up German paragraph with umlauts, a date, an amount and a made-up IBAN, as PNG and as JPEG at quality 0.55. Ask in German what it says. Never use a real document.
6. **Through the app.** The header `x-privateai-kind: image` on the request; the answer streams; the label under the answer; the allowance drops by `vision.allowanceCost`; the follow-up request is small again and has no picture; the eleventh picture of the day is refused with a readable message. Check that the reasoning-effort setting of the Fast mode is accepted together with a picture.
7. **The hosted path.** Through the Render bridge: the header arrives and a full-size picture question passes. Find out what the user sees when the bridge itself refuses a body over 1 MB.
8. **Real devices.** Drawing a box with a finger on an iPhone (Safari) and an Android phone (Chrome): `touch-action: none` on the picture means a drag draws and does not scroll. The camera path. A photo from an iPhone library (HEIC: the file input asks for PNG or JPEG; whether Safari converts was not checked). Desktop Chrome, Firefox, Safari. Screen reader: the tool's group label, the box list, the status messages.
9. **Real OCR suggestions.** The browser test used fake OCR words. With the real OCR data: a synthetic German letter, time on a phone, and how many of the planted identifiers get a box.
10. **The JPEG a real browser writes.** The test ran in headless Chromium, which adds a colour profile (APP2) that the strip removes. Check in Safari and Firefox that a picture still attaches (if their encoders write something the strip cannot remove, the tool refuses with "could not be prepared").
11. **Retention.** Ask Privatemode in writing, or find in its documents, that pictures are not stored, as for chat content, and whether a picture can sit in the prompt cache (we send a per-account `cache_salt`). Our texts say only what CometRow does.
12. **Face finder.** If any target browser has `FaceDetector`, try "Cover faces" on a synthetic or stock face. Otherwise accept that the layer is "draw boxes".

## Not built

- No blur and no face finder of our own (layer 4 above).
- No suggestion for names, addresses or anything the masking rules do not know.
- No more than one picture per message. No picture in a follow-up without attaching it again.
- No HEIC, WebP or GIF input, and no PDF pages as pictures.
- No use of `deepseek-ocr-2`.
- No zoom in the cover-up tool. On a phone a small detail is hard to hit; the box can be nudged with a keyboard only.
- No picture term in the spend guard, and the day count is not in the durable ledger (see shortcuts).
- No specific message for a relay refusal. The SDK hands the app only the status of a refused request, as for chat today. A user at the daily picture limit, without allowance or with a body the relay finds too large sees the general message ("The protected service is limiting requests" or "Protected response unavailable"), not the reason. The relay's own texts exist in English and German for the day this is passed through.
- No lock between attaching and a mode change: the "You chose Thinking" note is shown at the check step only.
